## What this is

A self-hosted household media catalog (books, CDs, DVDs) intended to run on a memory-constrained Raspberry Pi. Next.js App Router + Auth.js (next-auth v5 beta) + Drizzle ORM over Postgres. Barcode scanning (`@zxing/browser`) is a dependency but the `/scan` route it's meant to power doesn't exist yet — `site-header.tsx` already links to it.

## Note on the AGENTS.md warning above

One confirmed break already in this codebase, per `next@16.2.12`'s docs in `node_modules/next/dist/docs/`:

- **Middleware is now Proxy.** The root file is `proxy.ts`, not `middleware.ts`; the exported function/convention is called `proxy` (see `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`). This project's `proxy.ts` wraps `auth()` from `lib/auth.ts` directly instead of exporting a `proxy` function, and handles both the login redirect and the "already logged in, redirect away from /login" case.

npm run db:studio         # drizzle-kit studio

There is no test suite configured in this repo.

Required env vars (`.env.local`, not committed): `DATABASE_URL`, `AUTH_SECRET`.

## Architecture

**Auth flow**: `lib/auth.ts` configures Auth.js with a single Credentials provider (email/password checked against `users.passwordHash` via bcryptjs) and JWT sessions (the Credentials provider doesn't support database sessions in Auth.js). `role` (`"admin" | "member"`) is threaded from the DB user through the `jwt` and `session` callbacks — see the module augmentation in `lib/auth.d.ts`. `proxy.ts` is the perimeter guard: it redirects unauthenticated requests to `/login` (preserving the target as `callbackUrl`) and redirects authenticated users away from `/login`. Route/page-level code still re-checks `session.user.role` where it matters (e.g. `app/admin/users/page.tsx` redirects non-admins).

**Data layer**: `lib/db/schema.ts` defines two tables — `users` and `items` (the catalog entries, `mediaType` one of `book | cd | dvd | other`, with a `raw_metadata` jsonb column for whatever a future metadata-lookup source returns). `lib/db/index.ts` deliberately caps the postgres.js pool at 5 connections and reuses a single global client across dev hot-reloads — keep that pattern when touching DB setup, it's sized for a Pi, not for scaling up. Migrations live in `drizzle/`, generated by `db:generate` from `schema.ts` (don't hand-edit generated SQL).

**Server actions, not API routes, for mutations**: login (`app/login/actions.ts`), logout (`app/actions/auth.ts`), and admin user creation (`app/admin/users/actions.ts`) are all `"use server"` actions bound to forms via `useActionState`-style `(prevState, formData)` signatures, returning a string error message or `undefined` on success. The only route handler is the Auth.js catch-all at `app/api/auth/[...nextauth]/route.ts`. Follow this convention for new mutations rather than adding route handlers.

**Path alias**: `@/*` maps to the repo root (see `tsconfig.json`).
